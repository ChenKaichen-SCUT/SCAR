Goal obstacle repair (experimental, opt-in arm: obstacle)

Question
Which missing condition blocks the current task method, and which available
action can establish that condition or test how to establish it?

Implemented decision loop
1. Keep the existing actor, public task memory and actual-failure/repetition
   trigger. A warning is not an impossibility proof. Without a trigger, retain
   the actor's prompts, action and task memory.
2. Generate small conditional programs from observed dependencies. An output
   not already held/equipped can have missing inputs in an observed recipe.
   Acquire a visible input; follow observed routes to its last observed source;
   test an untraversed exit for that specifically missing item; or ask the
   observed task issuer about it. A failed route may have an observed alternate
   route or a previously observed resource used to open that same exit.
3. The LLM judges which missing condition matters now and selects a program id,
   or retains its original action. The gate cannot replace a retained original
   with an arbitrary lower-ranked alternative. New consuming/discarding actions
   are not generated by this layer. Capacity contradictions exclude pickups.
4. Execute one action, inspect its public result, and evaluate the program's
   local predicate. Acquisition needs an observed quantity; navigation needs
   observed location; source tests need the item in the current ground listing.
   Missing/uninformative dialogue is UNKNOWN, not a negative answer.
5. Execute at most one specified continuation after a known predicate result,
   fresh interface/capacity/failure checks, unchanged task and no urgent threat.
   Otherwise return control. Remember attempts in scoped public states for24
   steps. A task/held-resource change or expiry can allow another attempt.

What this does NOT establish
- Recipes constrain a proposed method; their ingredients are not added to the
  terminal task. Satisfied intermediate predicates do not prove task completion.
- Recipe backchaining is depth3 and roots depend on task wording and the actor's
  current method. It is not complete joint quantitative/resource planning.
- Traversed routes and old item locations may become stale. The first known
  edge is checked against recent failure, not every hidden lock on a future path.
- A reported unlocking transition plus one lost item is an observed association;
  it does not prove the item universally opens locks or preserves future resources.
- Task-issuer hints return to the actor on both outcomes. They are not executable
  discrimination policies and are not counted as successful active disambiguation.
  Even a term match in dialogue does not establish new information or useful advice.
- The gate checks dependencies, observations and local executability, not causal
  task value. The LLM's relevance judgment can still be wrong. Travel costs and
  other environmental resource losses are not covered by a safety theorem.

Evaluation
The protocol and amendment are under scar_public/experiments/. Baselines stay
frozen; the runner reuses historical API calls and audits every new transition.
Counterfactual one-step outcomes are evaluator-only. Main comparisons use full
300-action episodes. Selected old worlds are development data, not a holdout.
This arm is deliberately not the default until whole-task benefit is established.
