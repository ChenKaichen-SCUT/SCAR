# Stage28 预登记：失败反馈到恢复目标的工作流诊断

依据 `指引28.md`。本阶段只增加实验适配与离线分析，不开发新的 Agent、规划器或通用恢复机制。Stage27 的准确结论是“未确认主要瓶颈”，不是排除所有 State Grounding 机制。

## 冻结与样本

Stage25-AGC-v2、模型、基础 system/user prompt 生成链、环境、原始轨迹全部冻结；模型配置和绝对动作上限 300 与 Stage25 相同。新增代码单独位于 `scar_stage28`，不由 Agent 导入。

实验一复用 Stage27 穷举的 Stage26 数据：母轨迹 34 次公开拒绝，10 条相关 Oracle 分支 302 次，共 336 条。全都保留，独立母轨迹数为 1。观察后续 5/20 步及最终结局，少于 20 步为右删失，不当作完整失败。Stage A 用实际在线下一决策的 reasoning，绝不拿 Stage27 的专门解释回答替代在线理解。

## 唯一实验干预

仅在失败后**第一个决策**的所有原生重试请求末尾追加两段文字：`Temporary recovery objective` 和 `Original objective to resume after recovery`。具体目标字符串在代码和 checkpoint meta 中预先固定。

除此之外不修改 system prompt、原 observation、STM、控制器字段、动作仲裁或环境。目标只描述缺失条件，不含行动序列、位置、制作数量、配方、获取方法或隐藏知识。首次原始消息必须逐字等于保存的 Original 请求；第二个及后续决策完全恢复原输入生成链。

这是一次**恢复目标提示干预**，不是强制写入 controller.goal，也不保证模型采纳。是否采纳必须单独核验；若未采纳，不能把后续失败归因于“正确恢复目标下仍无法执行”。采纳后的目标维持与切换由原 AGC-v2 完成，不增加外部完成判定器或反复提醒。不给后续新失败再次注入目标。

## 恢复链指标

离线规则、命中句及原文全部保存。分析区分：

1. A：下一实际决策明确识别公开拒绝原因；并附前 5 步识别统计。
2. B：新的 goal_description 明确指向缺口，或 reasoning 中出现针对缺口的恢复意图。分别报告严格结构化新目标与较宽松的恢复意图，不把保持原泛化目标算新恢复目标。
3. C：有针对缺口且被接受的实际恢复动作；连续至少 2 个此类动作另报。动作被接受不能保证策略正确，重复丢下/捡回也可能命中代理指标。
4. D：在恢复行动之后，原失败动作真正执行成功，作为局部闭环的保守证据。字符串回到原目标另报，不等于任务恢复。不可装备、不可制作等本身无效目标不应被要求再次成功执行，单独列出不适用项。

没有明确证据表示未观察到/无法判定，不据最终失败反推未理解或未形成目标。此规则是可重算代理，不是全 336 条经独立人工语义评审；保留逐条轨迹供复核。不得仅依据阶段比例高低宣布 workflow 为唯一根因。

## 配对续跑评价

- 短期 5 步：原失败动作再次拒绝、原生拒绝总数、资源/位置/公开信息变化；资源增加和战斗信息不等同任务推进。
- 中期 20 步：恢复行动、连续恢复链、原失败动作成功、目标回归、主线增量。
- 长期：至原绝对 300 步上限或原 Agent 正常/异常终止，报告实际动作、第一章和主线奖励。
- 在 0/5/20/最后一步的隔离原生状态副本，离线尝试一次原失败动作，核验它现在是否可执行。探针不进入正式轨迹、不反馈给模型、不增加 API 调用。它是当前整体可行性的充分证据；探针仍失败不证明特定缺口没有被部分修复。
- 工具、工作台、材料等恢复目标的“完成”须有公开实际成功或原生探针支持；仅新目标文字不算完成。区分原失败动作实际恢复、探针可行、条件局部变化。

同一初始物理状态、记忆、控制器、模型与环境 RNG。Original 是保存样本，Oracle 是新模型采样，没有供应商配对随机种子。因此长期差异混入随机轨迹分叉，不能当成严格 isolated causal effect，也不是独立 10 个游戏。

Oracle 目标仅保证对应原失败动作公开的前置缺口，不保证该动作是完成更大目标的必要步骤。例如换一条合法路径或制作其他物品可能比恢复原动作更合理。原动作成功指标会遗漏这种有效替代；报告须结合主线、公开状态与具体案例判断。保持原目标也不等于没有恢复能力。

## 判定与止损

预登记描述标准：若 20 步内原失败动作实际成功的配对净改善至少 3/10，称明确局部改善；若最终主线改善至少 3/10 或第一章增加至少 3/10，称明确长期改善。其他情况报告混合/无明确收益。阈值不是显著性检验，也不用于调参。

局部与长期均提升且采纳明确，才支持进入恢复目标机制的下一阶段研究；仅局部提升但无长期提升为两层问题候选；均无明确提升不支持直接实现 Controller。未采纳与已采纳但执行失败必须分开，不能用无提升排除整个假设。

保持最多 10 并行（用户允许上限 12），保存全部模型请求、usage、费用、控制器决策、原生反馈和异常。既有语法重试/置信度重审不变；不追加实验重采样。代码、数据、检查点、冻结清单先提交 Git；完成后推送代码、统计、证据和报告，不上传下载依赖或凭据。
