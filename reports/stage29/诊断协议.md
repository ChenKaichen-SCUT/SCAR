## 生命周期定义

主要单位是每个检查点开始的恢复过程；初始恢复目标、原失败动作、较大的原目标三者分别记录。统计覆盖完整后缀，同时保留 Stage28 的 20 步口径供对照。后续中断/嵌套失败纳入完整时间线。

- Phase 0：Oracle 目标是否实际被模型提出并登记；Original 记录自发恢复意图，不把“没接受未提供的提示”当失败。
- Phase 1：实际理由是否理解临时缺口。只解释文字正确不代表完整状态理解正确。
- Phase 2：是否提出面向缺口的中间条件或步骤，另标局部可行、部分/依赖未解、与公开配方不符。不把计划错误、缺信息或未执行混成“没有分解”。
- Phase 3：分别记录临时条件公开达成证据、原失败动作成功、净资源进展、重复拒绝、目标中断、资源处置、后续结果。
- Phase 4：分别记录语义上的原目标重提、相关实际行动与真正任务进展。字符串不相等不等于遗忘；存档中存在不等于模型看见；恢复过程中死亡、资源损失、紧急战斗和合法替代目标分别说明。

阶段标签允许“部分/无法判断/不适用”；分母单独给出，不把无完成机会的窗口算作回归失败。手部容量释放可先于原动作重试，不以“未重试”推断条件未满足。仅持有变化不等于净增资源。

## Goal Stack 反事实

对每个检查点只用当时及此前公开的反馈构造分析用目标树，列出父目标、临时目标、已知子条件、结束/失效条件和仍未知的依赖。每个具体资源/条件要有公开原文来源与动作号；未知资源位置、制作方法保持未知。不得把后来的信息倒灌到初始树。

类型 A/B/C 是候选机制诊断，必须有具体目标、动作和上下文证据；不能仅凭最终失败断言遗忘或层级缺失。类型 D 记录即使保留目标关系仍需解决的状态、配方、探索、动作和资源约束，不能解释成已经通过 Stack 实验验证“永远无效”。允许多类重叠和无法隔离。

不将纸面目标树称为实际反事实结果；没有新模型重放就不能宣称 Goal Stack 已被证实有效或无效。可选 Oracle Goal Stack Replay 是否执行取决于前两项证据与可识别性，本轮不预设必跑。新增机制不在范围内。
