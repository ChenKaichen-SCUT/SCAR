# SCAR Stage 21：工程修复与证据触发的有界探索恢复（ETBR）

请继续推进 GitHub 仓库：

https://github.com/ChenKaichen-SCUT/SCAR

以零API审计提交 `2b272295ff2453ff970fd80e709b28479b379687` 为起点，基于Stage20冻结算法和Stage20A审计结论，开发独立的 `SCAR21`。

本轮研究目标是：

**解决游戏Agent在公开知识不完整时，因为候选遗漏或固定探索额度而过早停止的问题，并研究能否依据新获得的任务相关证据，有选择地恢复有限探索，从而重新推进原游戏任务。**

本轮只实现一个新研究机制：

**Evidence-Triggered Bounded Recovery（ETBR）：证据触发的有界探索恢复。**

必须将已有工程缺陷修复与ETBR机制明确分离。工程修复只是建立可靠基础，不得作为论文算法创新。

本轮不进入TTCL Challenge正式评测，不修改官方游戏环境，不开发复杂多步子目标新算法，也不重新引入负面后果记忆、LLM全局语义排序或多智能体结构。

## 一、已有审计结果与研究边界

Stage20A零API审计已确认：

- 11个停滞任务均存在可尝试的公开入口，但入口最终价值不一定已知。
- 7局存在不依赖探索额度限制的候选遗漏。
- 7局获得了相关新知识，却受到固定18次探索额度限制。
- 44次证据绑定拒绝中，32次属于可确定的字段匹配误拒，5次属于合理的待验证假设，7次应当拒绝。
- 264个负例测试未发生错误接受。
- `repair_kit` 和 `sharpened_blade` 存在新证据重新打开执行路径的局部原生案例。
- 复杂多步子目标没有获得足够证据支持其成为独立新算法。

此前完整任务成绩：

| 方法 | 成功数 | API请求 | 协议费用 |
|---|---:|---:|---:|
| SCAR18 | 14/24 | 885 | $0.870619 |
| SCAR19 | 12/24 | 290 | $0.294182 |
| SCAR20 | 12/24 | 191 | $0.511070 |

本轮首先解决工程缺陷，再验证ETBR是否有实际效果。

不得为了提高已有24题成功率而加入特定目标物品、地点、地图路径或隐藏制作配方的规则。

## 二、工程修复一：证据关系验证

重点修改Stage20的公开证据索引与校验接口。

目前 `evidence.py` 主要检查入口是否直接出现在证据记录的 `names` 中，导致部分合法地图入口被错误拒绝。

请建立**类型明确的公开证据关联检查**。

至少识别：

1. 对象名称与当前公开观察的关联。
2. 公开地图的 `from_location` 与目的地关系。
3. 当前已公开的直接路径和中转路径。
4. 对象历史公开位置与当前可访问位置的区别。
5. 材料、制作物及必要区域对象的公开关系。
6. LLM提出的入口是否确实存在且当前可执行。

特别注意区分：

- **入口真实性**：这个地点或对象是否已经公开、可访问？
- **目标相关性**：已有证据是否证明它有助于当前目标？

入口真实性需要严格验证。

目标相关性可以为UNKNOWN，因为未知规则探索本来就可能需要验证尚未确定的关系。

例如，公开证据证明courtyard能够作为前往barracks的中转点时，不应因为courtyard没有直接出现在被引记录的 `names` 字段而误拒。

但不能因为模型提到了某个不存在的地点，就自动创造合法入口。

以Stage20A保存的44个原始拒绝进行回归，分别统计能够修复的误拒、仍然合理的假设和必须拒绝的提案。

继续运行264个负例测试，确保没有凭空接受隐藏地点、未来证据、错误物品名称或不存在的路径。

## 三、工程修复二：公开地图中转候选

重点检查：

`exploration_entry()`

`_move()`

`locations()`

`public_entries()`

以及访问次数、候选去重、探索额度等相关逻辑。

Stage20的候选生成可能只检查相邻地点是否存在尚未探索的物品，而忽视一个地点可以作为通向更远公开入口的中转。

请改为基于**已经公开的游戏地图**组织探索入口。

要求：

- 保留公开地图的地点与连接关系。
- 对可达但非相邻的公开入口，能够提出实际的下一步中转移动。
- 中转地点即使没有新物品，也不应因此自动被认定没有探索价值。
- 遇到锁门或真实不可达反馈时，更新对应路径条件。
- 区分已经走过某个地点和已经完成该地点对应的探索目的。
- 将失败尝试记录与当前执行阻碍关联，避免永久禁止所有经过相同地点的后续路线。
- 每个移动仍计入真实环境动作预算，不能免费移动或修改地图。

重点回归审计中7个非额度候选遗漏案例，特别是 `cog_crossbow` 第20步遗漏的 `enter courtyard`。

不允许读取引擎隐藏地图直接为Agent提供路线。

## 四、工程修复三：简化子目标管理，停止复杂多步规划器研究

本轮停止扩展Stage19—20的复杂LLM持久多步子目标机制。

不再研究通过一个LLM提案生成完整材料取得链、工作台制作链或通用任务计划。

但必须保留原S1已有的确定性制作、材料取得、工作台条件检查、FIFO和P3收尾能力。这些属于游戏执行基础，不应一并删除。

建议将LLM职责收缩为：

**当控制器无法继续时，提出一个针对当前执行阻碍的、公开可执行的有限探索试探。**

LLM可以提出：

- 检查某个已公开对象。
- 访问某个已公开可达地点。
- 验证某条与当前任务有关但尚未证实的材料或规则假设。
- 获取解决当前阻碍所必需的一项公开信息。

它不负责输出完整多步执行计划，也不负责决定所有材料和工作台的操作顺序。

控制器只需要保存最小状态：

- 当前游戏目标。
- 当前未解决的执行阻碍。
- 已公开的证据。
- 当前待验证的探索试探。
- 实际执行结果。
- 是否能够返回原目标继续执行。

同时明确区分：

1. `PROBE_COMPLETED`：检查或移动已执行。
2. `NEW_EVIDENCE_OBTAINED`：得到了新的公开任务知识。
3. `PRECONDITION_RESOLVED`：必要执行条件实际满足或获得可执行路径。
4. `PARENT_TASK_RESUMED`：已经返回原任务执行。
5. `TASK_PROGRESS`：实际发生主任务进展。

一次检查成功不等于子目标全部完成，发现配方也不等于取得材料或成功制作。

不要把更长的意图持续时间作为目标，更不能为了提高多步完成率强制增加动作。

## 五、核心新机制：ETBR

### 5.1 研究对象应当是一般游戏内任务知识

ETBR不能设计成只适用于“制作物品”的特殊算法。

研究对象应当抽象为：

**当前游戏任务存在一个未满足的执行阻碍，而新的公开游戏知识可能改变这个阻碍的可解决性。**

这里的知识可以是：

- 新发现的物品制作关系。
- 新发现的材料来源或取得路径。
- 新发现的必要工作台或区域对象。
- 新发现的地图连接或可访问地点。
- NPC对话公开的任务线索。
- 门、钥匙、区域、任务阶段等执行条件。
- 真实反馈揭示的其他任务前提。

不要求本轮24个制作任务全部覆盖这些类型。

但是代码结构必须采用通用的公开任务证据与阻碍接口，避免将ETBR写成只识别 `craft`、`ingredient` 或 `station` 的专用补丁。

对于尚未支持的知识类型应明确返回UNKNOWN，不虚构解析能力。

未来TTCL主线任务可能涉及制作、移动、对话、战斗准备和任务阶段变化，因此机制本身应允许以后扩展到这些公开知识类型。

### 5.2 建立公开知识变化记录

每次真实环境反馈之后，更新一个 `PublicEvidenceDelta`。

建议记录：

- `evidence_id`
- `source_action`
- `observed_step`
- `knowledge_type`
- `subject`
- `relation`
- `object`
- `previous_status`
- `new_status`
- `related_blocker`
- `provenance`
- `freshness`

这里的证据必须来自真实公开观察、反馈或已公开知识的合法推导。

不能读取隐藏世界定义、评测器真值、未来轨迹或其他实验方法的运行结果。

**只有真正的新证据才有资格触发恢复。**

例如：

原来不知道 `rubble_chunk` 如何获得，现在公开了它需要 `rubble`，并且 `rubble_chunk` 位于当前任务的未完成必要依赖中。

这是有意义的相关新证据。

但以下情况不能自动触发：

- 重复检查已经知道的配方。
- 同一个证据只是更新时间戳。
- 发现与当前阻碍没有已公开关联的普通物品。
- LLM猜测某个地点可能有材料，但没有真实新反馈。
- 以前已经用于领取恢复机会的同一证据再次出现。

### 5.3 定义证据触发条件

当S1的正常执行与探索无法继续，或者固定探索额度已耗尽时，ETBR检查：

**条件A：当前是否仍然存在未解决的游戏执行阻碍？**

如果目标已经完成，不触发ETBR。

**条件B：是否存在尚未消费过、与当前阻碍有公开关系的新证据？**

例如新依赖、材料来源、必要前提或新地图连接。

**条件C：是否存在一个由当前公开状态支持的合法探索入口？**

探索入口必须可以通过正常游戏动作访问。

如果入口合法，但与目标的关系尚未证明，可以作为有限假设检验，而不是直接记为已知解决方案。

**条件D：本次恢复是否仍满足全局安全和预算限制？**

必须检查：

- 原始环境动作预算。
- 全局额外恢复额度。
- 当前阻碍的恢复额度。
- 当前入口的历史尝试情况。
- 已知无效或危险反馈。
- 模型请求和费用限制。

只有满足这些条件，才能追加恢复机会。

### 5.4 实现有界探索恢复

新增ETBR模块，建议独立实现为：

`scar_stage21/recovery.py`

核心过程：

1. 当前控制器遇到阻碍。
2. 检查最近公开知识的真实变化。
3. 判断新证据是否改变当前阻碍的可能解决路径。
4. 枚举可公开访问、尚未充分尝试的探索入口。
5. 若条件满足，发放一次小额恢复机会。
6. 通过S1执行对应公开探索动作。
7. 根据真实反馈更新知识。
8. 如果出现可执行路径，返回原控制器继续原游戏目标。
9. 如果没有获得有效证据，记录失败，不重复领取同一恢复机会。

**不能简单将固定探索上限18改成24、40或60，然后宣称实现了ETBR。**

ETBR必须通过新证据与当前阻碍之间的关系决定是否追加探索。

建议先采用简单、可冻结的有限预算：

- 原有18次探索额度保持不变。
- 单个新证据最多提供1次额外有效探索试探。
- 每个阻碍最多增加2次。
- 每局额外探索试探总数最多6次。
- 所有实际移动、检查和尝试仍计入100步环境动作。
- 如果一次有效探索需要中转移动，还必须设置有限的中转步数，不能通过一个探索信用无限移动。
- 同一证据对同一阻碍不得重复发放。
- 总模型调用次数不因ETBR无限增加。

以上数值可以在正式运行前通过工程可行性检查确定，但必须在冻结前固定，不得根据24个正式结果反复调节。

对于不存在相关新证据的任务，ETBR不应该凭空追加额度。

但工程修复后的正常公开入口搜索仍然可以继续工作，ETBR不能取代基本地图遍历。

### 5.5 不依赖额外复杂LLM规划

ETBR的证据检查、额度判断和恢复触发应尽量由确定性代码完成。

LLM仅在需要提出一个尚未验证的合法探索入口时按需调用。

每次调用应围绕一个具体阻碍，提供最少必要公开证据，不传入整个游戏历史。

如果确定性控制器已经知道合法恢复动作，不必再请求LLM。

保持结构化输出和公开证据ID校验，不重新开发复杂多步规划Schema。

每次恢复必须记录：

- 为什么触发。
- 是哪条新证据触发。
- 对应哪个当前阻碍。
- 使用了多少探索额度。
- 最终采取什么游戏动作。
- 是否获得进一步知识。
- 是否真正解除阻碍。
- 是否恢复原目标执行。
- 是否产生实际游戏进展。

## 六、零API工程验收与机制检查

在任何新付费实验前，先进行完整零API检查。

### 6.1 工程修复验收

必须复核：

- 44次历史证据拒绝。
- 264个负例。
- 7局非额度候选遗漏。
- 历史保存的公开地图与中转路线。
- 意图状态保存和恢复。
- Stage18—20已成功任务的关键确定性执行路径。

特别注意不能为了修复32次误拒而无条件接受所有提案。

### 6.2 ETBR机制验收

利用Stage20A保存的11个停滞状态进行影子决策测试，重点检查：

- 7个有相关新证据的额度限制案例。
- `repair_kit`检查 `rubble` 后产生新配方和下一步执行动作的情况。
- `sharpened_blade`检查 `iron_bar` 后重新发现制作关系的情况。
- `cog_crossbow`的普通中转候选遗漏是否由工程修复解决，而不是错误计入ETBR收益。
- 同一证据不能重复刷新额度。
- 无相关证据时不能无条件增加探索预算。
- 存在真实危险时不能自动忽略风险检查。
- ETBR状态经过保存和恢复后保持一致。

测试中可以在同物理状态、同RNG条件下执行少量原生单步反事实。

但是不能把这些单步分支结果当成新的完整任务成功率。

### 6.3 通用性接口测试

至少构造不包含隐藏答案的公开状态测试，覆盖：

- 制作前提缺失。
- 地图通路新公开。
- NPC对话提供新的任务条件。
- 任务阶段发生公开更新。

这些只是接口单元测试，不代表已经在其他完整游戏上取得泛化结果。

所有零API测试通过后才能冻结。

`results/stage17/tasks.json`

不得因为出现失败而调整算法、重新采样或选择性补跑。

本轮结果属于反复使用过的开发任务，不得宣称独立泛化。

## 八、需要重点评价的结果

### 8.1 整体性能

至少报告：

- R@60、R@80、R@100。
- 24题完整成功数。
- Robot Kingdom与Quarantine分别成功数。
- 原成功任务退化数量。
- 新增成功任务。
- 成功任务环境动作数。
- API请求数。
- 输入和输出tokens。
- 协议费用。
- 原生死亡、显式停滞及预算耗尽数量。

历史重点参照：

- Stage18：14/24，费用约$0.871。
- Stage20：12/24，费用约$0.511。

### 8.2 工程修复效果

记录：

- 原误拒规则实际修复情况。
- 新版本证据校验拒绝次数与原因。
- 中转路径候选实际执行次数。
- 以前会遗漏的公开入口是否被正常访问。
- 这些工程行为是否带来真实知识变化。

不能把这些工程修复产生的改善直接归功于ETBR。

### 8.3 ETBR机制效果

重点记录：

- ETBR触发次数。
- 合格新证据数量。
- 实际发放的额外探索额度。
- 额度的实际使用次数。
- 新证据与原阻碍之间的关系。
- 恢复后获得的新任务知识数量。
- 恢复后取得材料的次数。
- 恢复后满足必要执行前提的次数。
- 恢复后父任务实际制作或主任务进展的次数。
- 最终完整任务成功数。
- 无效恢复次数及对应的动作、HP和费用代价。

必须区分：

**ETBR允许额外探索 → 探索动作成功 → 获得新证据 → 解除前提 → 原任务恢复 → 最终完成。**

上述阶段不能合并为一个“恢复成功”指标。

### 8.4 剩余停滞原因

如果仍然出现 `STALLED`，必须说明：

- 是否存在未访问的合法公开入口。
- 是否只是当前策略未发现该入口。
- 是否存在相关新证据。
- ETBR额度是否已被使用。
- 是否确实缺少可支持的进一步动作。
- 当前环境动作预算还剩多少。
- 是否存在简单工程限制，而不是新算法能力不足。

不允许将“当前控制器没有动作”直接写成“游戏不可解”。

## 九、最终研究判断

本轮主要判断SCAR21能否在24题上形成值得继续研究的正面信号。
